# HG CORE OPERATING ARCHITECTURE

Status: TARGET ARCHITECTURE FOR MASTER GOVERNANCE RULESET V1
Scope: HG canonical operating process.

## 1. Purpose
HG is the governed operating core. Its runtime is generated by the new operating process and is not inherited from an earlier runtime.

## 2. Sole governing source
MASTER GOVERNANCE RULESET V1 is the only governing source. No other ruleset, policy, memory, configuration, or runtime may compete with or override it.

## 3. Canonical owner
`HG/core` is the canonical implementation and enforcement boundary for V1. Any generated runtime is subordinate to this source and must be verified against it.

## 4. Operating lifecycle
INTAKE -> CONTRACT -> AUTHORITY_CHECK -> PLAN -> EXECUTION -> OBSERVATION -> VERIFICATION -> EVIDENCE -> COMPLETION.

A failed or inconclusive step cannot silently become success. The process must continue through feasible corrective paths within the governing limits and record unresolved blockers accurately.

## 5. Runtime generation
Runtime is an operational result of the new process, not a required inherited component. The new process may create or reconstruct runtime state only from V1-bound contracts and verified inputs.

## 6. Ownership boundaries
The canonical core must not create competing policy, evidence, memory, replay, durable execution, or capability authorities. Each component has one explicit owner and a defined interface.

## 7. Verification and evidence
Every material change must be followed by relevant regression tests, negative tests, source/hash checks, and runtime verification when runtime execution is involved. Design intent alone is not runtime proof.

## 8. Learning and change
New knowledge is not automatically truth or authority. Promotion requires evidence and regression checks. No learning process may alter V1 or expand its own authority.

## 9. Negative boundaries
The following transitions are forbidden:
- observation -> truth without verification
- evidence -> authorization
- learning -> authority
- planning -> execution permission
- runtime state -> governing authority
- self-improvement -> automatic authority expansion
- incomplete tests -> release certification
- a reported action -> verified success without evidence

## 10. Cutover rule
The cutover target is a clean operating process governed by V1. Prior runtime implementations are not retained as active fallbacks. Unneeded project-specific files, loaders, configuration, and generated artifacts are removed from the target.

## 11. Acceptance
Acceptance requires:
- the exact approved V1 source is present and hash-bound;
- the implementation and every active consumer use V1 as the sole governing source;
- no legacy project runtime or policy remains in the target worktree;
- tests verify the V1 invariants and reject unauthorized overrides;
- post-change evidence is recorded;
- unresolved external scopes are explicitly marked NOT_APPLIED.

## 12. Boundary
This specification describes the target operating process. It does not by itself prove that the V1 source has been installed or that any remote runtime has been generated or verified.


## 13. V1 enforcement binding — local implementation

The V1 source is hash-pinned and enforced at the main HTTP runtime request boundary, the central model-inference gateway, the tool-governance executor, direct tool registry dispatch, and the locally available backend/edge/authority service entrypoints. A source or approval-binding mismatch must fail closed. Runtime health responses and tool execution witnesses identify the source hash.

The optional phone capability payload requires the exact source and approval binding in the phone user's `~/hg/` directory before serving any wrapped capability/base endpoint. Missing or mismatched policy blocks the request. This code change does not mean the payload has been installed on a phone.

VPS1, VPS2 and any other remote runtime are NOT_APPLIED until the exact V1 source and binding are provisioned there, the service code is updated, and post-deployment health/negative tests verify the governing hash. Local tests do not certify remote deployment.
